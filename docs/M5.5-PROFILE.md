# M5.5: admitted immutable harness execution profiles

Scope: Issue #25. M5.5 resolves the contract blocker found in the M6 (#17) preflight: Tsukai launched every harness with tools and extensions disabled and accepted only a prompt, so an orchestrator could not run a real coding agent (tools, a governance guard, a custom tool, a chosen provider/model) through Tsukai. M5.5 adds a typed, versioned, admitted execution profile to AgentRun creation. It does not start M6, move any orchestration policy into Tsukai, or change workspace or process ownership.

## Authority

| Owner                           | Responsibility                                                                                                                                                                      |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Caller (orchestrator, operator) | Execution policy: which provider/model, which tools, which extensions/guards a run may have                                                                                         |
| Tsukai                          | Validation against the selected adapter, immutable binding to the AgentRun, deterministic projection into the harness-native invocation, durable identity, capability advertisement |
| Harness                         | Native semantics of the projected flags                                                                                                                                             |
| Nawabari                        | Workspace/filesystem authority (unchanged: `RunCreateInput.workspace` is the admitted scope)                                                                                        |
| Jinushi                         | Physical process ownership (unchanged: the projected argv is submitted as one Jinushi Run)                                                                                          |

Tsukai never decides policy. It has no notion of any particular orchestrator's tool set, guard, or model choice.

## Contract

```ts
interface ExecutionProfile {
  schemaVersion: 1;
  provider?: string;
  model?: string;
  tools?: (
    | { source: "builtin"; name: string }
    | { source: "extension"; extension: string; name: string }
  )[];
  extensions?: { id: string; path: string; sha256: string }[];
}
```

`runs.create({ ..., executionProfile })`. There is no argv, environment, cwd, or workspace field; unknown fields are rejected. Validation happens before anything is persisted or started:

- `schemaVersion` must be 1.
- `provider` matches `^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$` and `model` matches `^[A-Za-z0-9][A-Za-z0-9._:/@+-]{0,255}$`. A leading alphanumeric excludes option-like (`-`), file-argument (`@`), and home-relative (`~`) values; whitespace and commas are excluded.
- Tools (at most 32) have unique names matching `^[A-Za-z][A-Za-z0-9_-]{0,63}$`. A `builtin` tool must be in the adapter's advertised `tools.builtin` list. An `extension` tool must name a declared extension and may not shadow a built-in name.
- Extensions (at most 8) have unique ids (`^[a-z0-9][a-z0-9._-]{0,63}$`), unique paths, and unique content. `path` is absolute, normalized, and has no control characters; `sha256` is 64 lowercase hex digits. Tsukai opens the file, requires a regular non-symlink file whose canonical path is the path given, at most 4 MiB, and whose SHA-256 equals the declaration. The same check is repeated by the Jinushi port immediately before the Run is submitted. Package sources (`npm:`, `git:`, `https:`, `builtin:`) are not accepted: only admitted, content-addressed local files.

Failures are typed `ExecutionProfileError` (`EXECUTION_PROFILE_INVALID` for malformed input, `EXECUTION_PROFILE_UNSUPPORTED` for a dimension the adapter does not configure) with `harness` and `dimension`; the owner IPC carries the same codes. Error messages name the dimension and extension id, never a path. A runtime without profile support (the M0 mock, or an adapter over a port that cannot project a profile) rejects any profile instead of ignoring it.

## Normalization and identity

The effective profile bound to the run is:

```ts
interface EffectiveExecutionProfile {
  schemaVersion: 1;
  fingerprint: string; // sha256:<hex>
  provider?: string;
  model?: string;
  tools: ExecutionProfileTool[]; // sorted by name
  extensions: { id: string; sha256: string }[]; // sorted by id (load order)
}
```

The fingerprint is the SHA-256 of the canonical JSON array `[schemaVersion, provider|null, model|null, tools, extensions]` with tools as `["builtin", name]` or `["extension", extensionId, name]` and extensions as `[id, sha256]` (`executionProfileFingerprint`). Equivalent profiles (any input order) normalize to the same effective profile, fingerprint, and argv. Extension content (digest), not its path, is its identity; paths are locators, used once to build the invocation, and are never persisted, journaled, or returned.

The effective profile is set at creation and has no mutation path. Snapshots, list results, and projections return copies; later edits to an extension file do not change the run (a changed file is refused at submission).

## Composition with the workspace

Profile and workspace are two separate immutable inputs to one AgentRun. `workspace.cwd`/`workspaceSessionId` remain the caller's already-admitted (Nawabari) scope and become the Jinushi Run's cwd exactly as before. The profile cannot set cwd, add filesystem roots, change `workspaceSessionId`, or bypass admission: it has no such fields and unknown fields fail. An extension path is code the caller admits by digest, not a directory granted to the agent. Tools act inside the harness process whose cwd is the admitted workspace; Tsukai is still not an OS sandbox or a filesystem policy engine.

A scoped agent (M3) cannot admit a profile: `agent_spawn` with an `executionProfile` is `FORBIDDEN`, and children keep default deny. Operator admission is the only path.

## Default deny

Without a profile, nothing changes: the Pi argv is still `--mode rpc --no-session --no-extensions --no-skills --no-prompt-templates --no-themes --no-context-files --no-approve --no-tools` and the Claude Code argv still ends with `--tools ""`, byte-for-byte (`test/profile/profile.test.ts`). Snapshots carry no `executionProfile`, and journals are unchanged. An empty profile (`{ schemaVersion: 1 }`) is also default deny, with an effective profile recorded.

## Capabilities

`HarnessCapabilities.executionProfile` (per adapter, over its execution port):

| Dimension    | Pi 0.99.1                                                   | Claude Code 2.1.285                              |
| ------------ | ----------------------------------------------------------- | ------------------------------------------------ |
| `provider`   | `configurable` (native `available`), `requiresModel: true`  | `unsupported` (native `absent`)                  |
| `model`      | `configurable`, verification `exact`                        | `configurable`, verification `reported`          |
| `tools`      | `configurable`, builtin `bash edit find grep ls read write` | `unsupported` (native `available`), builtin `[]` |
| `extensions` | `configurable` (native `available`)                         | `unsupported` (native `unverified`)              |

A port that does not declare `executionProfile: "projected"` (for example the M1a direct certification runner) makes every dimension `unsupported`. The Jinushi Pi and Claude Code ports declare it.

## Pi projection

Verified against the published `@earendil-works/pi-coding-agent@0.99.1` artifact (`dist/cli/args.js`, `dist/main.js`, `dist/core/sdk.js`, `dist/core/model-resolver.js`, `dist/core/resource-loader.js`, `dist/core/agent-session.js`, `dist/core/tools/index.js`):

- `--provider` is applied only together with `--model` (`buildSessionOptions`), so a provider without a model is invalid.
- `--tools a,b` is an exact allowlist over built-in, extension, and custom tools and takes precedence over `--no-tools` (`allowedToolNames = options.tools ?? …`); without `--tools`, `--no-tools` leaves no tool active.
- Explicit `--extension <path>` files load despite `--no-extensions` (discovered extensions stay disabled). An extension load failure or an unresolved model makes Pi exit before RPC starts, which Tsukai records as physical evidence, never success.
- Built-in tool names are `allToolNames` minus the Windows-only `powershell`.

The projection appends, after the fixed default-deny arguments: `--provider P`, `--model M`, `--tools <sorted names>`, then one `--extension <path>` per extension in id order. Custom tools (for example an orchestrator's read-only execution-facts tool) are registered by an admitted extension and admitted by name; a guard is an admitted extension (Pi `tool_call` handlers can block calls).

Pi resolves `--model` patterns fuzzily and accepts `:thinking` suffixes. Tsukai therefore reads the model Pi reports in `get_state` and requires an exact match (provider case-insensitive, model id or `provider/id`); otherwise the run settles as `failed`/`pi-model-mismatch` before the prompt is written. Profiled runs journal a `harness.profile` observation with the fingerprint, `modelVerified`, and the reported provider/model id.

## Claude Code

Verified against the installed Claude Code 2.1.285 `--help`: `--model` accepts an alias or full name and `system/init` reports the resolved model (already recorded under `claudeCode`). Only the model is projected (`--model M`, verification `reported`). There is no provider selector (`unsupported`). Tools stay `unsupported`: the fixed launch uses `--permission-mode dontAsk`, and the permission contract for enabled tools is not verified for this adapter, so `--tools ""` remains fixed. Plugins/hooks are skipped by `--bare` and not admitted. Requests for unsupported dimensions fail with `EXECUTION_PROFILE_UNSUPPORTED` before Jinushi is contacted.

## Durability and recovery

The effective profile is part of the durable snapshot (`runs/<id>.json`) and of every `run.snapshot` journal record; loading and replay whitelist its fields strictly (replay also re-checks the fingerprint). Restart never relaunches, resends the prompt, or re-projects anything, so no profile can be re-applied differently. Before re-attaching a nonterminal profiled run, reconciliation requires:

- the persisted fingerprint still covers the persisted fields; otherwise `uncertain`/`execution-profile-drift`;
- the adapter now registered still configures every dimension the profile uses; otherwise `uncertain`/`execution-profile-unsupported`.

Adapter or version mismatch keeps the M5 reasons. Terminal runs are unchanged. Nothing silently falls back to default deny or another profile.

## Privacy

Persisted and journaled: schema version, fingerprint, provider, model, tool names and sources, extension ids and digests. Never persisted or journaled: extension paths, prompts, assistant text, tool arguments/results, environments, credentials. The M4 projection shows the same safe metadata (`FleetRun.executionProfile`, and `profile=… provider=… model=… tools=… extensions=…` in the text renderer, only for profiled runs).

- `test/profile/profile.test.ts`: default-deny argv for Pi and Claude Code, empty profile, Pi coding profile acceptance and exact projection, model-only/tools-only projection, Pi model mismatch before prompt, 28 malformed/injection cases plus symlink and pre-submission re-verification, Claude Code unsupported dimensions and model projection, mock/non-projecting port rejection, normalization and fingerprint stability, immutability, restart preservation without relaunch/resend, drift and unsupported-adapter uncertainty, workspace non-widening, `agent_spawn` refusal and IPC error codes, metadata-only journal and state, live/replay projection agreement and tampered-replay rejection, capabilities.
- `scripts/test-package.mjs`: the packed package constructs a profile, reads capabilities, creates a profiled run through the resident owner IPC, inspects the effective profile, checks the submitted Jinushi argv/cwd, and type-checks the public types.
- `pnpm run certify:profile` (needs a running Jinushi supervisor: `TSUKAI_JINUSHI_STATE_DIR`, `TSUKAI_JINUSHI_WORKSPACE`; the certified Pi as in M1b): starts the real `tsukai owner serve` process over real Jinushi and Pi 0.99.1 and runs lanes with an admitted certification provider extension (Pi's own scripted `fauxProvider`, credential-free) and an admitted guard extension that blocks `git push` and registers a custom tool. Lanes: a tool-enabled run that edits an isolated workspace, is blocked by the guard, and uses the custom tool; tools default-deny inside a profile; exact tool allowlist; exact model; no-profile M5 behavior; owner SIGKILL and restart with the same AgentRun, Jinushi Run, and profile and no resent prompt. Provider-backed semantic success is a separate lane (`TSUKAI_PI_LIVE_PROVIDER`, `TSUKAI_PI_LIVE_MODEL`) reported `ENVIRONMENT_BLOCKED` without credentials.

Limitations: Tsukai cannot observe Pi's active tool set directly (Pi RPC has no command for it); the allowlist is enforced by Pi's documented flag semantics and certified behaviorally. Extension files are verified at admission and at submission; Tsukai cannot prevent a same-user process from changing a file between submission and Pi's own load. Claude Code tools and extensions remain unsupported.
